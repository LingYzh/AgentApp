# Chat context controls

- The chat composer now shows a compact, color-segmented context-estimate bar. It uses only the local `ContextWindows` estimate and uses the configured model capacity only when `ProviderConfig.contextWindowFor()` supplies one. An unknown capacity is explicitly marked as unconfigured instead of assuming a default window; its bar still shows the estimate's category composition.
- Tapping the bar opens a bottom sheet with estimated context categories, their relative shares, any saved compaction count, and the latest provider-reported token usage. Cache read/write numbers are shown as input subsets and are never added into a total.
- Main conversations can request `ContextCompactor` from this sheet. The confirmation explains that compaction changes future provider context while retaining original messages. Compression is cancellable and locks sending, attachment changes, and history edits until its job finishes. Child conversations remain read-only.
- A per-conversation reasoning selector keeps `null` as “follow model configuration”; selecting `NONE` remains an explicit provider override. It can change during generation and is saved on the shared conversation, so the next provider request uses it without interrupting the HTTP request already underway.
- Editing or deleting history clears `contextCompaction` and `lastContextUsage` before saving, because either record would otherwise describe obsolete conversation state. The send preflight checks attachments from `ContextWindows.replay(conversation)`, so attachments covered by a compaction summary do not incorrectly block a later request.
